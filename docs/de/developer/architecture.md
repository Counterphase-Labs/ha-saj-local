# Architektur

Wie die SAJ-Bibliothek und die Integration aufgeteilt sind und warum das Projekt so gebaut ist, wie es gebaut ist.

Jeder folgende Abschnitt nennt die Abschnitte der Funktionsliste der Integration, deren Zeilen `Files:` den Code auflisten, den der Abschnitt beschreibt. Die Funktionsliste besitzt, was jeder Teil tut, und die Seite erklärt, warum der Code so gebaut ist.

## Wie das Projekt aufgeteilt ist

Vier Teile, absichtlich getrennt gehalten:

- **SAJ-Bibliothek** (`custom_components/saj_local/saj/`): alles über SAJ-Geräte und Modbus. Die Bibliothek darf Home Assistant nicht importieren, damit sich die Gerätelogik mit einfachen Eingaben testen lässt. Die Bibliothek wird innerhalb der Integration ausgeliefert; die Trennung ist eine Entwurfsgrenze, kein Paket.
- **Home-Assistant-Integration** (der Rest von `custom_components/saj_local/`): Einrichtungsablauf, Entitäten, Diagnose, Übersetzungen. Halte die Integration dünn. Logik, die auch ohne Home Assistant gelten würde, gehört in die Bibliothek.
- **Frontend** (`frontend/`): die Lovelace-Karten. Die Build-Ausgabe wird ins Verzeichnis der Integration geschrieben, weil HACS das Verzeichnis als ein Archiv ausliefert.
- **Modbus-Simulator** (`mock/`): ein eigenes Programm, das keinen Code mit den anderen teilt. Siehe [die Simulatorseite](simulator.md).

Die Import-Verträge unter `[tool.importlinter]` in `pyproject.toml` setzen diese Grenzen in `make import-lint` durch.

## Geräteprofile

Die Abschnitte der Funktionsliste [Einrichtung und Erkennung](../../../custom_components/saj_local/docs/features.md#setup-and-detection) und [Geräte und Entitäten](../../../custom_components/saj_local/docs/features.md#devices-and-entities) listen den Code auf.

Die Bibliothek enthält keinen Code pro Modell. Ein Modell ist eine Deklaration `Profile`, die Klasse in `saj/models/__init__.py` und je ein Wert in `saj/models/hs3.py` und `saj/models/h2.py`: die Gerätetypcodes mit ihren Formen, die Registerplatzierungen mit ihren Belegen, die Familien, die Ersetzungen, die Ausstattungsprüfungen, die Methoden der Leistungssteuerung, die Fehlerzuordnung und ob der Registervertrag von Hand verifiziert ist. Ein Identitätsleser und ein Telemetrieleser bedienen jedes Profil, und `resolve_profile` in `saj/profiles.py` ist die eine reine Funktion, die das Modell aus dem gemeldeten Gerätetyp und der Auswahl des Benutzers bestimmt.

Halte die Bibliothek so: Ein Modell, das dieselben Register verwendet, ist ein neuer Wert `Profile` und sonst nichts. Eine Verzweigung auf ein bestimmtes Profil, in der Bibliothek oder in der Integration, ist ein Defekt. Die Integration baut das Dropdown Modell aus `PROFILES` und nennt nie ein Modell.

Ein erkannter Gerätetyp ist maßgeblich, daher kann keine Auswahl die Bibliothek dazu bringen, ein erkanntes Gerät als anderes Modell zu behandeln. Das erkannte Modell wird nie gespeichert; das Modell wird jedes Mal aus dem Gerät abgeleitet, und nur die Auswahl des Benutzers wird gespeichert. Einrichtung und Konfigurieren teilen eine Validierungsroutine, damit beide dieselben Ergebnisse erzwingen.

Die Modellfehler der Bibliothek liegen in `saj/errors.py`, und ein Vertrag von import-linter erlaubt nur dem `errors.py` der Integration, dieses Modul zu importieren. Das `errors.py` der Integration ist die einzige Stelle, die diese Fehler in Übersetzungsschlüssel und Platzhalter umwandelt, daher braucht ein neuer Fehler eine Änderung in `errors.py` und nirgendwo sonst.

## Optionale Ausstattung

Der Abschnitt der Funktionsliste [Optionale Ausstattung](../../../custom_components/saj_local/docs/features.md#optional-equipment) listet den Code auf.

Zeilen optionaler Ausstattung tragen ein explizites Feld `equipment` in ihrer `Definition`, gesetzt dort, wo die Schlüssel oder Familien definiert sind, und nie aus dem Schlüsseltext abgeleitet. Der Katalog liefert die Zeilen eines Gerätetyps und einer Menge vorhandener Ausstattung (`Fit`), sodass Telemetrie, Last, Steuerung und die Entitäten alle von derselben Menge ausgehen, und Zeilen von Ausstattung, die nicht vorhanden ist, werden nie geplant, gelesen, in einer Abfragegruppe angeboten oder beschreibbar gemacht. Ein Profil deklariert pro Ausstattungsteil, das es haben kann, ein `Probe`: Bedingungen auf Katalogschlüsseln, von denen jede die Ausstattung findet, und was eine unbeantwortete Prüfung bedeutet. Die Katalogerstellung weist eine Prüfung zurück, deren Schlüssel fehlt, nicht lesbar ist oder selbst mit Ausstattung markiert ist, und einen kombinierten Wert, dessen Quellen zu anderer Ausstattung gehören, sodass ein Prüfschlüssel auf jeder Einheit immer existiert.

Die Erkennung (`saj/detection.py`) liest jeden Prüfschlüssel der geprüften Ausstattung in einem geplanten Lesezugriff über den Telemetrieleser, sodass Prüfungen, deren Schlüssel einen Block teilen, eine Anfrage teilen; ein Modell mit Zeilen für mehr als ein Batteriepack fügt demselben Lesezugriff die Packanzahl hinzu. Eine Verweigerung oder ein nicht dekodierbarer Wert ist eine Antwort und folgt dem unbeantworteten Ergebnis der Prüfung, und eine verweigerte Anfrage lässt jede Prüfung unbeantwortet, die sie trug; eine verlorene Verbindung oder ein Timeout ist keine Antwort und lässt die Einrichtung wie jeder andere Lesezugriff fehlschlagen. Die Entscheidung, was vorhanden ist, aus der Einstellung, der gemerkten Menge und den Prüfergebnissen ist eine reine Funktion in `saj/equipment.py`, ebenso die Packgrenze: die höchste gültige gesehene Anzahl, vergessen bei einer Batterie, die auf Nicht vorhanden gesetzt wird. Die Integration (`equipment.py`) speichert die gemerkte Menge und die Packgrenze vor dem Laden der Plattformen in den Daten des Eintrags, sodass kein Neuladen ausgelöst wird, meldet gemerkte Ausstattung, die nicht mehr erkannt wird (eine Protokollwarnung, ein Diagnose-Flag und eine Reparaturmeldung pro Installation und Ausstattung), und entfernt die Registereinträge von Zeilen, die nicht zur Ausstattung gehören. Die Einstellungen sind Optionen des Eintrags; die gemerkte Menge und die Packgrenze sind Daten des Eintrags, die Konfigurieren beim Speichern erhält und die beim Ersetzen der Einheit verworfen werden.

Wo ein Modell keine von Hand verifizierten Messwerte hat, sind seine Belege gereiht: Werkzeuge im Feld im dauerhaften Einsatz und Feldberichte zuerst, dann das Dokument des Modells, und der Simulator nie. Eine Zeile übernimmt den Beleg der besten Quelle, die sie abdeckt, sodass eine Zeile, die Feldberichte bestätigen, `IMPLEMENTED` und standardmäßig aktiviert ist, und eine Zeile, die nur das Dokument definiert, `DOCUMENTED` ist und deaktiviert erstellt wird. Wo das Englisch des Dokuments dem Chinesisch widerspricht, wird das Chinesisch verwendet. Ein Wort ohne Bedeutung (reservierte oder durchgereichte Wörter) ist keine Entität und bleibt im Registerabbild. Einstellungen, die ein falscher Wert gefährlich machen würde, werden bei ihrer Katalogisierung zu `COMMISSIONING_KEYS` hinzugefügt, sodass ein Modell nie eine beschreibbare Zeile bereitstellt, die nicht durch Zufall geschützt ist.

Beide Modelle legen die Netzbezugs- und Einspeisesummen auf die Zähler aller Phasen und die Zähler der ersten Phase als Zeilen `grid_l1_*`, sodass die Schlüssel bei beiden Modellen dasselbe bedeuten. Die Batterieidentität des H2 ist eine nach Pack indizierte Familie (`battery_pack_identity`), fünf Mitglieder mit festem Abstand; die Packgrenze gilt für sie wie für jede andere Packzeile, und die höchste Packzeile eines Modells legt sein Packmaximum fest, weshalb das Maximum des H2 fünf ist, während seine Familien für Zustand, Fehler und Energie bei vier enden.

Ob eine Zeile standardmäßig aktiviert ist, folgt der Kernmarkierung der Zeile bei Zähler A, Zähler B, der Wallbox und dem Parallelsystem (`ENABLED_WITHOUT_EVIDENCE` in `saj/models/__init__.py`), weil diese Zeilen nur existieren, wenn die Ausstattung vorhanden ist. Batterie- und Wechselrichtermesswerte behalten die Belegregel, während eine als Kern markierte beschreibbare Einstellung unabhängig von ihrem Beleg standardmäßig aktiviert ist, weil die Belegschranke Messwerte schützt, auf die sich ein Benutzer verlassen könnte, und keine Einstellung, die der Benutzer bewusst ändert, und dieselbe Einstellung bei beiden Modellen denselben Standard hat. Packzeilen tragen den Packindex über die Familienrolle `PACK`, und die Packgrenze des `Fit` entfernt die Zeilen darüber. Eine Zahl kann negiert werden (`Definition.negated`, `Format.negated`), so werden die Leistungen von Zähler A, die im Register beim Bezug positiv sind, bei der Einspeisung positiv gelesen wie jede andere Netzleistung; Zähler B ist ein Solarzähler und wird nicht negiert. Ein Bitfeld kann invertiert werden (`Definition.inverted`, `Format.inverted`), im Codec dekodiert und kodiert, so zeigt `ev_ems_charging` Laden an, wenn das Registerbit 0 ist, während das Lesen-Ändern-Schreiben des gepackten Felds die anderen Bits erhält. Die `Replacement` eines Modells kann einen kombinierten Schlüssel in ein einzelnes adressiertes Register verwandeln (`uncombined`), so liest der H2 jede Parallelleistung aus einem 16-Bit-Register, während der HS3 unter denselben Schlüsseln weiter niedriges und hohes Wort kombiniert.

## Abfrage

Die Abschnitte der Funktionsliste [Abfrage](../../../custom_components/saj_local/docs/features.md#polling) und [Den Wechselrichter schützen](../../../custom_components/saj_local/docs/features.md#protecting-the-inverter) listen den Code auf.

Die Bibliothek entscheidet, was wann gelesen wird, und schützt das Gerät; die Integration stellt nur das Ergebnis dar. Die Abfrageregeln liegen in der Bibliothek, weil die Regeln das Gerät beschreiben und nicht Home Assistant, sodass kein Code der Integration die Regeln umgehen kann.

- **Zeitplan, Budget, Gesundheit und Abfrager** (`saj/schedule.py`, `budget.py`, `health.py`, `poller.py`) besitzen je eine Entscheidung und nehmen Zeit und Warten als Eingaben. Keines der vier Module liest eine Uhr oder schläft, wodurch ihre Tests sofort und deterministisch laufen. Nur die Standardwerte des Clients und die Verdrahtung des Koordinators berühren echte Zeit.
- **Ein gemeinsames Zeitraster pro Installation.** Gegeneinander versetzte Taktungen würden nie eine Anfrage teilen; ein gemeinsames Raster lässt zusammenfallende Ticks gemeinsam planen, und das Verwerfen verpasster Ticks verhindert, dass ein Überlauf zum Rückstau wird.
- **Das Anfragebudget ist eine Eigenschaft des Geräts.** Das Budget zählt Anfragen, weil Feldberichte Anfragen beschreiben, und das Budget ist eine Konstante der Bibliothek und keine Einstellung, damit keine Konfiguration das Budget überschreiten kann. Das Warten auf das Budget verlängert einen Zyklus, statt Lesezugriffe zu verwerfen.
- **Eine Antwort wird klassifiziert, nicht als bestanden oder fehlgeschlagen behandelt.** Ein verweigertes Register ist eine Antwort eines gesunden Geräts und betrifft nur seine Sensoren; nur Codes für beschäftigt und Gerätefehler und Verbindungsfehler lassen einen Zyklus fehlschlagen. Ein verweigerter Block kann daher nicht jede Entität flackern lassen.
- **Fehlgeschlagene Zyklen weichen zurück und wiederholen nie innerhalb des Zyklus.** Wiederholungen vervielfachen die Last genau dann, wenn ein Modul Mühe hat. Die einzige Ausnahme ist eine veraltete gehaltene Verbindung, die kein Gerätefehler ist: Die Verbindung wird neu geöffnet, die Identität geprüft, und der Zyklus wird zu einem vollständigen Lesezugriff, sodass kein veröffentlichter Wert älter ist als die Wiederverbindung.
- **Das Budget und das Zurückweichen gehören zum Endpunkt, nicht zu einem Laden** (`saj/guard.py`). Ein Neuladen, eine Gruppenänderung oder eine Wiederholung der Einrichtung baut einen neuen Client, und ein vom Client gehaltenes Budget oder eine Fehlerzahl finge jedes Mal bei null an, wodurch ein Modul von den eigenen Wiederholungen von Home Assistant bedrängt wird. Die Integration hält pro Host und Port einen Wächter in `hass.data` für die Lebensdauer von Home Assistant und gibt ihn jedem Client und Abfrager, einschließlich des temporären Clients einer Einrichtung oder einer Prüfung von Konfigurieren. Das Laden fragt zuerst den Wächter und meldet nicht bereit, bevor es eine Verbindung öffnet, und eine vom Benutzer gestartete Prüfung umgeht das Zurückweichen, aber nicht das Budget. Eine bestandene Prüfung setzt das Zurückweichen zurück, da das Gerät gerade geantwortet hat und das folgende Laden nicht wegen eines bereits geheilten Fehlers abgelehnt werden soll; eine fehlgeschlagene Prüfung ändert nichts, sodass ein Benutzer, der eine falsche Adresse erneut versucht, den Schutz weder verlängern noch löschen kann.
- **Abfragegruppen sind Untereinträge der Konfiguration.** Ein Untereintrag gibt nativ Hinzufügen, Bearbeiten und Löschen auf der Integrationsseite, ohne Einrichtung oder Konfigurieren zu ändern. Eine Gruppe speichert semantische Entitätsschlüssel (`keys`), nie Entitäts-IDs, und Entitäten werden nie an einen Untereintrag gehängt, weil Home Assistant die Entitäten eines gelöschten Untereintrags löscht und eine Gruppe einen Sensor oder seinen Verlauf nicht mitnehmen darf.
- **Zustand wird nur für Sensoren geschrieben, die gelesen wurden,** oder deren Verfügbarkeit sich geändert hat, damit eine schnelle Gruppe langsame Sensoren nicht aktualisiert aussehen lässt.
- **Aufweckzeiten werden aufgerundet.** Home Assistant plant einen Koordinator auf ganze Sekunden, und ein zu früh ausgelöstes Aufwecken fände nichts Fälliges und verschwendete einen Slot.

## Gerätefehler und Reparaturen

Die Abschnitte der Funktionsliste [Gerätefehler und Reparaturen](../../../custom_components/saj_local/docs/features.md#device-faults-and-repairs) und [Modellwechsel](../../../custom_components/saj_local/docs/features.md#model-replacement) listen den Code auf.

Ein Fehler ist ein modellneutraler Schlüssel mit einem Namen bei jedem Modell, das ihn meldet. Ein Modell legt in seinem `Profile.faults` (`saj/models/hs3.py`, `h2.py`) fest, welche Bits welcher Fehlerwörter jeden Schlüssel melden, und die Fehlerwörter selbst sind gewöhnliche platzierte Zeilen, die nie Entitäten sind (`Definition.exposed` ist falsch). Bitpositionen sind Daten, daher ändert ihre Korrektur keinen Schlüssel. Zustände, die beide Modelle gleich melden, werden in `saj/models/shared_faults.py` geteilt; ein Modell listet nur auf, worin es sich unterscheidet.

Der Katalog baut die Fehlerentitäten aus dieser Zuordnung und nicht aus Platzierungen: ein benannter Fehler, eine nicht erkannte Zeile und eine Zusammenfassungszeile pro Ausstattungsteil mit Fehlerwörtern, jede eine kombinierte Zeile, deren Operation `ANY_BIT` die Bits ihrer Quellwörter prüft. Die Zusammenfassung liest auch die Fehlerwörter der Batteriepacks, die einfache Zeilen der Familie `battery_pack_faults` sind. Die Katalogerstellung weist ein Wort zurück, das keine platzierte Zeile ist, eine Quelle, die in keinem Fehlerwort oder außerhalb ihres Worts liegt, ein Bit, das zwei Fehler beanspruchen, und einen Fehler, dessen Wörter zu anderer Ausstattung gehören. Fehlerzeilen sind unabhängig von ihrem Beleg standardmäßig aktiviert, weil der Benutzer das für jeden Fehler so gewählt hat, und der Planer hält ihre Quellwörter in der Anfrage, die ohnehin gestellt wird, wo der Block sowieso gelesen wird. `hidden_sources` gibt dem Koordinator die Wörter hinter den aktivierten Fehlerentitäten, damit sie gelesen werden, auch wenn keine Entität sie zeigt, und die Diagnose und das Fehlerprotokoll verwenden die rohen Wörter. Das Dekodieren von Wörtern zu aktiven Fehlern und nicht erkannten Bits und die Überwachung, die zwei Messungen in ausgelöste und aufgehobene Fehler verwandelt, sind reiner Bibliothekscode (`saj/faults.py`).

Alle Problem-IDs, ihr Auslösen und ihre Entfernung liegen in `issues.py`: die Probleme zu Ausstattung, Modell, Verweigerung und Nichterreichbarkeit. Bibliotheksfehler werden dort nie importiert; `errors.translate_error` liefert den Übersetzungsschlüssel und die Platzhalter, die entscheiden, ob ein Fehler ein Modellbefund ist. Das Verweigerungsproblem behält seine Schlüssel in seinen Problemdaten, sodass ein Neuladen, das ein frisches `ReadHealth` startet, einen Schlüssel trotzdem aufheben kann, der jetzt antwortet. Das Problem der Nichterreichbarkeit liest die Zeit des Fehlschlagens seit dem Wächter des Endpunkts (`saj/guard.py`), die Neuladen wie der Rest des Wächters überlebt, und wird bei jedem fehlgeschlagenen Zyklus und jedem Ladeversuch geprüft, einschließlich eines Ladens, das durch das Zurückweichen beendet wurde.

Die Behebungen sind Reparaturabläufe von Home Assistant (`repairs.py`). Die Behebung des Modells dupliziert Konfigurieren nicht: `EntryChanges` in `config_flow.py` enthält die Validierung, die Konfliktprüfungen und das Speichern, die Konfigurieren und die Reparatur teilen, und die Reparatur ruft `EntryChanges` mit den gespeicherten Einstellungen und dem Modell auf Automatisch auf. Bei einer geladenen Installation leiht sich die Validierung den Client des Koordinators (`async_validation_session`), der am Ende der Sitzung geschlossen wird, auch bei einem Fehler. Die Sitzung fordert dann eine Aktualisierung an, als Task geplant, damit das Formular nicht auf eine Abfrage wartet, und ausgeführt, nachdem die Sperre des Zyklus freigegeben wurde. Diese Abfrage sieht einen getrennten Client und verbindet sich über `Poller._reopen` neu, das die Identitätsprüfung hält; ein verbundener Client würde die Identitätsprüfung überspringen, und bis die Prüfung lief, würden Schreibzugriffe und Heartbeats als nicht verbunden abgelehnt. Das Problem der Nichterreichbarkeit erscheint beim ersten fehlgeschlagenen Wiederholungsversuch nach 15 Minuten, was das Zurückweichen auf 15 bis 20 Minuten nach Beginn eines Ausfalls legt.

## Debug-Dump und Protokollierung

Der Abschnitt der Funktionsliste [Diagnose und Debug-Protokollierung](../../../custom_components/saj_local/docs/features.md#diagnostics-and-debug-logging) listet den Code auf.

Der Registerspeicher (`saj/memory.py`) liegt in `ModbusTcpClient`, weil der Client die eine Stelle ist, die jeder Lesezugriff durchläuft: Abfragen, Heartbeats, Rücklesen nach Schreibzugriffen, Erkennung und Identität speisen den Speicher ohne eigenen Code. Der Speicher zeichnet beantwortete Wörter pro Adresse und fehlgeschlagene Bereiche pro Adresse und Anzahl auf, mit der eigenen Uhr des Clients, damit Tests keine echte Zeit brauchen. Jede `ModbusErrorMessage`, die die Leitung erreichen kann, wird in `FAILURE_OUTCOMES` auf eines von vier Ergebnissen abgebildet: Verweigerungen sind `exception`, beide Timeouts sind `timeout`, ein fehlgeschlagener Verbindungsaufbau, ein Schließen durch die Gegenseite und eine unvollständige Antwort sind `connection_lost`, und ein nicht passender Header oder eine fehlerhafte Länge, Registeranzahl oder Bestätigung ist `malformed_reply`. Eine verweigerte Spanne oder ein verweigerter Wert erreicht die Leitung nie und wird nicht gemerkt. Schreibzugriffe werden nicht als Lesezugriffe gemerkt. Ein Fehler wird verworfen, wenn derselbe Bereich antwortet, und Wörter behalten ihr eigenes Alter, sodass ein Dump zeigt, was zuletzt gut war und was seitdem fehlgeschlagen ist. Der Schnappschuss wird bei Bedarf aus den Katalogzeilen des Geräts gebaut, daher kostet das Gruppieren nach Schlüssel beim Abfragen nichts.

Der Datenschutz wird dort entschieden, wo die Wörter sind, nicht dort, wo sie gezeigt werden. `Definition.private` markiert die Zeilen, deren Inhalt eine Person oder ein Netzwerk identifiziert; `private_rows` gibt sie plus den Seriennummernbereich des Wechselrichters, den keine Zeile abdeckt, den aber die Identität und der Identitätsblock des H2 lesen. Der Schnappschuss enthält private Wörter nie, nicht einmal für die Integration, und markiert stattdessen den Eintrag; `diagnostics.py` setzt den Schwärzungsmarker von Home Assistant ein, was die Bibliothek frei von Home Assistant hält. Ein Lesezugriff, der nur einen Teil einer privaten Zeile abdeckt, wird ganz verborgen, sodass eine teilweise Überlappung kein Wort preisgeben kann. Der Validierungsclient der Formulare von Einrichtung, Konfigurieren und Reparatur darf den Dump nicht verschmutzen: Konfigurieren bei einem geladenen Eintrag verwendet den Client des Koordinators wieder, daher umhüllt `async_validation_session` ihn mit `ModbusTcpClient.unremembered`.

Die Protokollierung (`saj/log.py`) muss jeder Zeile ein Systemlabel geben und den Debug-Schalter pro Integration von Home Assistant am Funktionieren halten. `LabelledLogger`, ein `LoggerAdapter`, gebaut aus dem eigenen Logger jedes Moduls, tut beides, weil der Loggername unverändert bleibt und nur die Nachricht das Präfix erhält. Das Label wird aus dem Titel des Eintrags und der Seriennummer gebaut, mit der der Eintrag erstellt wurde, die bekannt ist, bevor die Identität gelesen wurde, sodass schon die erste Zeile einer Einrichtung ein Label trägt, und das Label maskiert die Seriennummer, die der Standardtitel enthält, damit die vollständige Seriennummer nie in ein Protokoll gelangt. `label.py` baut das Label für Module der Integration, und die Einrichtung gibt denselben Text an jedes Bibliotheksobjekt weiter, das einen eigenen Adapter baut. Eine Abfragezeile wird vom Abfrager aus den Anfragen zusammengesetzt, die durch seinen zählenden Leser gingen, sodass eine fehlgeschlagene Abfrage trotzdem die Anfragen meldet, die sie gestellt hat, einschließlich einer, die von der Frist des Zyklus abgeschnitten wurde und als Timeout aufgeführt wird.

## Stabile Namen

Die Abschnitte der Funktionsliste [Geräte und Entitäten](../../../custom_components/saj_local/docs/features.md#devices-and-entities) und [Entitäts-IDs und Präfix](../../../custom_components/saj_local/docs/features.md#entity-ids-and-prefix) listen den Code auf.

Entitätsschlüssel sind ein Vertrag mit jedem Dashboard und jeder Automatisierung, die ein Benutzer schreibt. Die Bibliothek stellt einen Satz von Namen, Einheiten und Formaten über SAJ-Modelle hinweg dar, sodass ein Hardware-Upgrade den Verlauf überall behält, wo sich das alte und das neue System überlappen. Bilde ein neues Gerät auf das vorhandene Vokabular ab, bevor du Namen erfindest.

Entitäts-IDs sind Teil desselben Vertrags. `object_id` und `fixed_entity_id` in `const.py` sind die einzige Stelle, die das Format definiert, und alles andere (die Entitäten, das Umbenennen bei einer Präfixänderung, der Bestätigungstext, die Diagnose) ruft die beiden Funktionen auf. Ein Entitätsschlüssel ist daher Teil einer Entitäts-ID: Einen Schlüssel umzubenennen ist eine inkompatible Änderung, eine Bezeichnung umzuformulieren nicht. Die eindeutige ID einer Entität bleibt die ID des Konfigurationseintrags plus der Schlüssel (`entity_unique_id`) und wird von einer Präfixänderung nicht berührt. Das Präfix ist ein Anliegen von Home Assistant und liegt nur in den Optionen des Eintrags der Integration, nie in der SAJ-Bibliothek.

Eine Präfixänderung benennt über das Entitätsregister um, weil der Recorder nur so Verlauf und Statistiken zur neuen ID mitnimmt. Der Recorder weigert sich, Statistiken auf eine ID zu verschieben, die bereits welche hat, daher wird die Änderung zuerst mit einer Metadatenabfrage (`async_list_statistic_ids`) geprüft, und jede Prüfung wird beim Speichern der Änderung vor der ersten Umbenennung wiederholt.

## Schreibzugriffe

Die Abschnitte der Funktionsliste [Einstellungen ändern](../../../custom_components/saj_local/docs/features.md#changing-settings), [EMS](../../../custom_components/saj_local/docs/features.md#ems) und [Leistungssteuerung](../../../custom_components/saj_local/docs/features.md#power-control) listen den Code auf.

- **Schreibzugriffe haben einen Pfad.** Eine Aktion einer Entität ruft `SajEntity.async_change` auf, das die einzige Methode `write` des Koordinators aufruft. Die EMS-Bereinigung verwendet dieselbe Sperre und dieselbe Fehlerbehandlung. Der Heartbeat ist kein Schreibzugriff: Der Heartbeat liest das Ziel jeder eigenen Funktion über `keep_alive_read_ems` der Bibliothek, dann die EMS-Grenzen über das Lesen der Grenzen, unter derselben Zyklussperre, und verbraucht keine Schreibzuteilung. Nur `custom_components/saj_local/errors.py` darf die Fehler der Bibliothek importieren; der Rest geht darüber.
