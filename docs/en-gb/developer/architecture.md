# Architecture

How the SAJ library and the integration are divided, and why the project is built the way it is.

Each section below names the integration feature list sections whose `Files:` lines list the code the section describes. The feature list owns what each part does, and the page explains why the code is built the way it is.

## How the project is divided

Four parts, kept apart on purpose:

- **SAJ library** (`custom_components/saj_local/saj/`): everything about SAJ devices and Modbus. The library must not import Home Assistant, so device logic can be tested with plain inputs. The library ships inside the integration; the split is a design boundary, not a package.
- **Home Assistant integration** (the rest of `custom_components/saj_local/`): config flow, entities, diagnostics, translations. Keep the integration thin. Logic that would be true without Home Assistant belongs in the library.
- **Frontend** (`frontend/`): the Lovelace cards. The build output is written into the integration directory because HACS ships that directory as one archive.
- **Modbus simulator** (`mock/`): a separate program that shares no code with the others. See [the simulator page](simulator.md).

The import contracts under `[tool.importlinter]` in `pyproject.toml` enforce these boundaries in `make import-lint`.

## Device profiles

The feature list sections [Setup and detection](../../../custom_components/saj_local/docs/features.md#setup-and-detection) and [Devices and entities](../../../custom_components/saj_local/docs/features.md#devices-and-entities) list the code.

The library holds no per-model code. A model is a `Profile` declaration, the class in `saj/models/__init__.py` and one value each in `saj/models/hs3.py` and `saj/models/h2.py`: the device type codes with their shapes, the register placements with their evidence, the families, the replacements, the equipment probes, the power control methods, the fault map and whether the register contract is hand-verified. One identity reader and one telemetry reader serve every profile, and `resolve_profile` in `saj/profiles.py` is the one pure function that resolves the model from the reported device type and the selection of the user.

Keep the library that way: a model that uses the same registers is a new `Profile` value and nothing else. A branch on a specific profile, in the library or in the integration, is a defect. The integration builds the Model dropdown from `PROFILES` and never names a model.

A recognised device type is authoritative, so no selection can make the library treat a recognised device as another model. The detected model is never stored; the model is derived from the device each time, and only the selection of the user is saved. Setup and Configure share one validation routine so both enforce the same outcomes.

The library's model errors live in `saj/errors.py`, and an import-linter contract allows only the integration's `errors.py` to import that module. The integration's `errors.py` is the single place that turns those errors into translation keys and placeholders, so a new error needs an edit in `errors.py` and nowhere else.

## Optional equipment

The feature list section [Optional equipment](../../../custom_components/saj_local/docs/features.md#optional-equipment) lists the code.

Rows of optional equipment carry an explicit `equipment` field on their `Definition`, set where the keys or families are defined and never derived from the key text. The catalogue serves the rows of a device type and a set of fitted equipment (`Fit`), so telemetry, load, control and the entities all work from the same set, and rows of equipment that is not fitted are never planned, read, offered in a polling group or writable. A profile declares one `Probe` per piece of equipment it can have: conditions on catalogue keys, any of which finds the equipment, and what an unanswered probe means. Catalogue construction rejects a probe whose key is missing, unreadable or itself tagged with equipment, and a combined value whose sources belong to other equipment, so a probe key always exists on every unit.

Detection (`saj/detection.py`) reads every probe key of the equipment being probed in one planned read through the telemetry reader, so probes whose keys share a block share a request; a model with rows for more than one battery pack adds the pack count to the same read. A refusal or an undecodable value is an answer and follows the probe's unanswered result, and a refused request leaves every probe it carried unanswered; a lost connection or a timeout is not an answer, and fails setup like any other read. The decision of what is fitted from the setting, the remembered set and the probe results is a pure function in `saj/equipment.py`, as is the pack limit: the highest valid count seen, forgotten with a battery set to Not fitted. The integration (`equipment.py`) stores the remembered set and the pack limit in the entry data before the platforms load, so no reload is triggered, reports remembered equipment that is no longer detected (a log warning, a diagnostics flag and a repair issue per installation and equipment), and removes the registry entries of rows that are not in the fit. The settings are entry options; the remembered set and the pack limit are entry data, which Configure preserves when Configure saves and drops when the unit is replaced.

Where a model has no hand-verified readings, its evidence is ranked: field tooling in sustained use and field reports first, then the model's document, and the simulator never. A row takes the evidence of the best source that covers it, so a row field reports confirm is `IMPLEMENTED` and enabled by default, and a row only the document defines is `DOCUMENTED` and created disabled. Where the document's English contradicts its Chinese the Chinese is used. A word with no meaning (reserved or pass-through words) is not an entity and stays in the register snapshot. Settings that a wrong value would make dangerous are added to `COMMISSIONING_KEYS` when they are catalogued, so a model never exposes a writable row that is not protected by accident.

Both models place the grid import and export totals on the all-phase counters and the first-phase counters as `grid_l1_*` rows, so the keys mean the same on both. The H2 battery identity is one family indexed by pack (`battery_pack_identity`), five members at a fixed stride; the pack limit applies to it like every other pack row, and the highest pack row a model has sets its pack maximum, which is why the H2 maximum is five while its state, fault and energy families stop at four.

Whether a row is enabled by default follows the core mark of the row for Meter A, Meter B, the EV charger and the parallel system (`ENABLED_WITHOUT_EVIDENCE` in `saj/models/__init__.py`), because those rows exist only when the equipment is fitted. Battery and inverter readings keep the evidence rule, while a writable setting marked core is enabled by default whatever its evidence, because the evidence gate guards readings a user could rely on, not a setting the user chooses to change, and the same setting has the same default on both models. Pack rows carry the pack index through the `PACK` family role, and the fit's pack limit removes the rows above it. A number can be negated (`Definition.negated`, `Format.negated`), which is how the Meter A powers, positive on import in the register, read positive on export like every other grid power; Meter B is a solar meter and is not negated. A bit field can be inverted (`Definition.inverted`, `Format.inverted`), decoded and encoded in the codec, which is how `ev_ems_charging` shows charging on when the register bit is 0 while the packed-field read-modify-write keeps the other bits. A model's `Replacement` can turn a combined key into a single addressed register (`uncombined`), which is how the H2 reads each parallel power from one 16-bit register while the HS3 keeps combining low and high words under the same keys.

## Polling

The feature list sections [Polling](../../../custom_components/saj_local/docs/features.md#polling) and [Protecting the inverter](../../../custom_components/saj_local/docs/features.md#protecting-the-inverter) list the code.

The library decides what to read and when, and protects the device; the integration only presents the result. Polling rules live in the library because the rules describe the device, not Home Assistant, so no integration code can bypass the rules.

- **Schedule, budget, health and poller** (`saj/schedule.py`, `budget.py`, `health.py`, `poller.py`) each own one decision and take time and waiting as inputs. Nothing in the four modules reads a clock or sleeps, which is what lets their tests run instantly and deterministically. Only the client's defaults and the coordinator's wiring touch real time.
- **One shared time grid per installation.** Cadences that are offset from each other would never share a request; a common grid lets coincident ticks be planned together, and dropping missed ticks stops an overrun from becoming a backlog.
- **The request budget is a device property.** The budget counts requests, because requests are what field reports describe, and the budget is a library constant rather than a setting so that no configuration can exceed the budget. Waiting for the budget lengthens a cycle instead of dropping reads.
- **A response is classified, not treated as pass or fail.** A refused register is an answer from a healthy device and affects only its sensors; only busy and device-failure codes and link errors fail a cycle. One refused block therefore cannot make every entity flap.
- **Failed cycles back off and never retry inside the cycle.** Retries multiply load exactly when a module is struggling. The single exception is a stale kept connection, which is not a device failure: the connection is reopened, the identity is verified and the cycle becomes a full read so no published value predates the reconnect.
- **The budget and the back-off belong to the endpoint, not to a load** (`saj/guard.py`). A reload, a group edit or a setup retry builds a new client, and a budget or failure count held by the client would start from zero each time, which is how a module gets hammered by Home Assistant's own retries. The integration keeps one guard per host and port in `hass.data` for the life of Home Assistant and gives it to every client and poller, including the temporary client of a setup or Configure check. Loading asks the guard first and reports not ready before opening a connection, and a check started by the user bypasses the back-off but not the budget. A check that passes resets the back-off, since the device has just answered and the load that follows should not be refused for a failure that has already healed; a failed check changes nothing, so a user retrying a bad address cannot extend or erase the protection.
- **Polling groups are config subentries.** A subentry gives native add, edit and delete on the integration page without changing Setup or Configure. A group stores semantic entity keys (`keys`), never entity IDs, and entities are never attached to a subentry, because Home Assistant deletes the entities of a deleted subentry and a group must not take a sensor or its history with it.
- **State is written only for sensors that were read** or whose availability changed, so a fast group does not make slow sensors look refreshed.
- **Wake-ups are rounded up.** Home Assistant schedules a coordinator on whole seconds, and a wake-up that fires early would find nothing due and waste a slot.

## Device faults and repairs

The feature list sections [Device faults and repairs](../../../custom_components/saj_local/docs/features.md#device-faults-and-repairs) and [Model replacement](../../../custom_components/saj_local/docs/features.md#model-replacement) list the code.

A fault is a model-neutral key with one name on every model that reports it. A model states, in its `Profile.faults` (`saj/models/hs3.py`, `h2.py`), which bits of which fault words report each key, and the fault words themselves are ordinary placed rows that are never entities (`Definition.exposed` is false). Bit positions are data, so correcting one changes no key. Conditions that both models report the same way are shared in `saj/models/shared_faults.py`; a model lists only what it differs in.

The catalogue builds the fault entities from that map instead of from placements: a named fault, an unrecognised row and a summary row per piece of equipment that has fault words, each a combined row whose `ANY_BIT` operation tests the bits of its source words. The summary also reads the battery pack words, which are plain rows of the `battery_pack_faults` family. Catalogue construction rejects a word that is not a placed row, a source that lies in no fault word or outside its word, a bit that two faults claim and a fault whose words belong to other equipment. Fault rows are enabled by default whatever their evidence, because the user chose that for every fault, and the planner keeps their source words in the request that is already made where the block is read anyway. `hidden_sources` gives the coordinator the words behind the enabled fault entities, so they are read even though no entity shows them, and diagnostics and the fault log use the raw words. Decoding of words to active faults and unrecognised bits, and the watch that turns two readings into raised and cleared faults, are pure library code (`saj/faults.py`).

All issue IDs, their raising and their removal live in `issues.py`: the equipment, model, refusal and unreachable issues. Library errors are never imported there; `errors.translate_error` supplies the translation key and placeholders that decide whether an error is a model finding. The refusal issue keeps its keys in its issue data, so a reload, which starts a fresh `ReadHealth`, can still clear a key that now answers. The unreachable issue reads the endpoint guard's failing-since time (`saj/guard.py`), which survives reloads like the rest of the guard, and is checked at every failed cycle and every load attempt, including a load ended by the back-off.

The fixes are Home Assistant repair flows (`repairs.py`). The model fix does not duplicate Configure: `EntryChanges` in `config_flow.py` holds the validation, the conflict checks and the save that Configure and the repair share, and the repair calls `EntryChanges` with the saved settings and the model set to Automatic. For a loaded installation the validation borrows the coordinator's client (`async_validation_session`), which is closed when the session ends, even on failure. The session then requests a refresh, scheduled as a task so the form does not wait for a poll and run after the cycle lock is released. That poll sees a disconnected client and reconnects through `Poller._reopen`, which holds the identity check; a connected client would skip the identity check, and until the check ran writes and heartbeats would be refused as not connected. The unreachable issue appears at the first failed retry after 15 minutes, which back-off makes 15 to 20 minutes into an outage.

## Debug dump and logging

The feature list section [Diagnostics and debug logging](../../../custom_components/saj_local/docs/features.md#diagnostics-and-debug-logging) lists the code.

The register memory (`saj/memory.py`) lives in `ModbusTcpClient`, because the client is the one place every read passes through: polls, heartbeats, write read-backs, detection and identity all feed the memory with no code of their own. The memory records answered words per address and failed ranges per address and count, with the client's own clock so tests need no real time. Each `ModbusErrorMessage` that can reach the wire maps to one of four outcomes in `FAILURE_OUTCOMES`: refusals are `exception`, both timeouts are `timeout`, a failed connect, a peer close and an incomplete response are `connection_lost`, and a mismatched header or a malformed length, register count or acknowledgement is `malformed_reply`. A refused span or value never reaches the wire and is not remembered. Writes are not remembered as reads. A failure is dropped when the same range answers, and words stay with their own age, so a dump shows both what was last good and what has failed since. The snapshot is built on demand from the device's catalogue rows, so grouping by key costs nothing while polling.

Privacy is decided where the words are, not where they are shown. `Definition.private` marks the rows whose content identifies a person or a network; `private_rows` gives them plus the inverter serial range, which no row covers but which identity and the H2 identity block read. The snapshot never carries private words at all, not even to the integration, and marks the entry instead; `diagnostics.py` substitutes Home Assistant's redaction marker, which keeps the library free of Home Assistant. A read that covers only part of a private row is hidden whole, so a partial overlap cannot leak a word. The validation client of Setup, Configure and the repair forms must not pollute the dump: Configure on a loaded entry reuses the coordinator's client, so `async_validation_session` wraps it in `ModbusTcpClient.unremembered`.

Logging (`saj/log.py`) has to give every line a system label and keep Home Assistant's per-integration debug switch working. `LabelledLogger`, a `LoggerAdapter` built from the own logger of each module, does both, because the logger name is unchanged and only the message gains the prefix. The label is built from the entry title and the serial the entry was created with, which is known before identity has been read, so even the first line of a setup is labelled, and the label masks the serial, which the default title contains, so the full serial never reaches a log. `label.py` builds the label for integration modules, and setup passes the same text to every library object, which builds an adapter of its own. A poll line is assembled by the poller from the requests that went through its counting reader, so a failed poll still reports the requests it made, including one cut off by the cycle deadline, which is listed as a timeout.

## Stable names

The feature list sections [Devices and entities](../../../custom_components/saj_local/docs/features.md#devices-and-entities) and [Entity IDs and prefix](../../../custom_components/saj_local/docs/features.md#entity-ids-and-prefix) list the code.

Entity keys are a contract with every dashboard and automation a user writes. The library presents one set of names, units and formats across SAJ models, so a hardware upgrade keeps history wherever the old and new systems overlap. Map a new device onto the existing vocabulary before inventing names.

Entity IDs are part of the same contract. `object_id` and `fixed_entity_id` in `const.py` are the only place the format is defined, and everything else (the entities, the rename on a prefix change, the confirmation text, diagnostics) calls the two functions. An entity key is therefore part of an entity ID: renaming a key is a breaking change, rewording a label is not. The unique ID of an entity stays the config entry ID plus the key (`entity_unique_id`) and is untouched by a prefix change. The prefix is a Home Assistant concern and lives only in the integration's entry options, never in the SAJ library.

A prefix change renames through the entity registry because that is what makes the recorder carry history and statistics to the new ID. The recorder refuses to move statistics onto an ID that already has them, so the change is checked first with one metadata lookup (`async_list_statistic_ids`) and every check is repeated when the change is saved, before the first rename.

## Writes

The feature list sections [Changing settings](../../../custom_components/saj_local/docs/features.md#changing-settings), [EMS](../../../custom_components/saj_local/docs/features.md#ems) and [Power control](../../../custom_components/saj_local/docs/features.md#power-control) list the code.

- **Writes have one path.** An entity action calls `SajEntity.async_change`, which calls the coordinator's single `write` method. The EMS cleanup uses the same lock and error handling. The heartbeat is not a write: the heartbeat reads each owned function's target through `keep_alive_read_ems` of the library, then the EMS limits through the limits read, under the same cycle lock, and uses no write allowance. Only `custom_components/saj_local/errors.py` may import the library's errors; the rest go through it.
