# 架构

SAJ 库和集成如何划分，以及项目为何这样构建。

下面每一节都会指出集成功能列表中的相应章节，这些章节的 `Files:` 行列出了该节所描述的代码。功能列表负责说明每个部分做什么，本页说明代码为何这样构建。

## 项目如何划分

四个部分，有意相互分开：

- **SAJ 库**（`custom_components/saj_local/saj/`）：关于 SAJ 设备和 Modbus 的一切。该库不得导入 Home Assistant，这样设备逻辑就可以用普通输入来测试。该库随集成一起发布；这种划分是设计边界，而不是一个软件包。
- **Home Assistant 集成**（`custom_components/saj_local/` 的其余部分）：配置流程、实体、诊断、翻译。保持集成精简。不依赖 Home Assistant 也成立的逻辑属于库。
- **前端**（`frontend/`）：Lovelace 卡片。构建输出写入集成目录，因为 HACS 把该目录作为一个压缩包发布。
- **Modbus 模拟器**（`mock/`）：一个独立的程序，与其他部分不共享任何代码。参见[模拟器页面](simulator.md)。

`pyproject.toml` 中 `[tool.importlinter]` 下的导入契约在 `make import-lint` 中强制执行这些边界。

## 型号配置

功能列表的 [设置与检测](../../../custom_components/saj_local/docs/features.md#setup-and-detection) 和 [设备与实体](../../../custom_components/saj_local/docs/features.md#devices-and-entities) 两节列出了相关代码。

库中没有按型号编写的代码。型号是一个 `Profile` 声明，即 `saj/models/__init__.py` 中的类，以及 `saj/models/hs3.py` 和 `saj/models/h2.py` 中各自的一个值：设备类型代码及其形态、寄存器布局及其依据、系列、替换项、设备探测、功率控制方法、故障映射，以及寄存器约定是否经过手动验证。一个标识读取器和一个遥测读取器服务于每个型号配置，`saj/profiles.py` 中的 `resolve_profile` 是根据上报的设备类型和用户的选择解析型号的唯一纯函数。

请保持库的这种状态：使用相同寄存器的型号只是一个新的 `Profile` 值，别无其他。在库或集成中针对某个特定型号配置做分支，就是缺陷。集成从 `PROFILES` 构建“型号”下拉列表，从不指名任何型号。

已识别的设备类型具有权威性，因此没有任何选择可以让库把已识别的设备当作另一个型号。检测到的型号从不存储；型号每次都由设备推导，只保存用户的选择。设置和“配置”共用一个验证例程，因此两者强制执行相同的结果。

库的型号错误位于 `saj/errors.py`，import-linter 契约只允许集成的 `errors.py` 导入该模块。集成的 `errors.py` 是把这些错误转换为翻译键和占位符的唯一位置，因此新增一种错误只需编辑 `errors.py`，别处都不用改。

## 可选设备

功能列表的 [可选设备](../../../custom_components/saj_local/docs/features.md#optional-equipment) 一节列出了相关代码。

可选设备的行在其 `Definition` 上带有明确的 `equipment` 字段，在定义键或系列的地方设置，绝不从键的文字推导。目录提供某个设备类型和一组已安装设备（`Fit`）的行，因此遥测、负载、控制和实体都基于同一组设备工作，未安装设备的行绝不会被规划、读取、提供给轮询组或写入。型号配置为其可能拥有的每一种设备声明一个 `Probe`：对目录键的条件，其中任何一个满足即发现该设备，以及未应答的探测意味着什么。目录构建会拒绝其键缺失、不可读或本身被标记了设备的探测，也会拒绝其来源属于其他设备的组合值，因此探测键在每台设备上始终存在。

检测（`saj/detection.py`）通过遥测读取器，在一次规划好的读取中读取被探测设备的每个探测键，因此键位于同一数据块的探测共用一次请求；具有多个电池包的行的型号，会把电池包数量加入同一次读取。被拒绝或无法解码的值就是一种应答，并按该探测的未应答结果处理，被拒绝的请求会使其所携带的每个探测都处于未应答；连接丢失或超时不是应答，会像任何其他读取一样使设置失败。根据设置、已记住的集合和探测结果来决定哪些设备已安装，是 `saj/equipment.py` 中的一个纯函数，电池包上限也是如此：见过的最大有效数量，在电池被设为“未安装”时会被忘记。集成（`equipment.py`）在平台加载之前，把已记住的集合和电池包上限存入条目数据，因此不会触发重新加载；它会报告不再被检测到的已记住设备（每个安装和每种设备一条日志警告、一个诊断标志和一个修复问题），并移除不在已安装集合中的行的注册表条目。设置是条目选项；已记住的集合和电池包上限是条目数据，“配置”在保存时保留这些数据，在更换设备时丢弃这些数据。

在某个型号没有手动验证的读数时，其依据按以下顺序排列：持续使用的现场工具和现场反馈在前，其次是该型号的文档，模拟器绝不作为依据。一行采用覆盖该行的最佳来源的依据，因此现场反馈所确认的行是 `IMPLEMENTED` 并默认启用，只有文档定义的行是 `DOCUMENTED` 并以禁用状态创建。当文档的英文与中文矛盾时，采用中文。没有含义的字（保留字或透传字）不是实体，保留在寄存器快照中。错误的值会带来危险的设置，在编入目录时会被加入 `COMMISSIONING_KEYS`，因此型号绝不会因疏忽而暴露出不受保护的可写行。

两个型号都把电网购电和馈电总量放在全相计数器上，并把第一相计数器作为 `grid_l1_*` 行，因此这些键在两个型号上含义相同。H2 的电池标识是一个按电池包编号的系列（`battery_pack_identity`），共五个成员，步长固定；电池包上限与其他每个电池包行一样适用于该系列，型号拥有的最高电池包行决定其电池包最大值，这就是 H2 的最大值是五，而其状态、故障和电量系列止于四的原因。

对于电表 A、电表 B、充电桩和并机系统，一行是否默认启用取决于该行的核心标记（`saj/models/__init__.py` 中的 `ENABLED_WITHOUT_EVIDENCE`），因为这些行只有在设备已安装时才存在。电池和逆变器读数保留依据规则，而标记为核心的可写设置无论依据如何都默认启用，因为依据门槛保护的是用户可能依赖的读数，而不是用户选择更改的设置，并且同一个设置在两个型号上的默认值相同。电池包行通过 `PACK` 系列角色携带电池包编号，已安装集合的电池包上限会移除超出上限的行。数值可以取负（`Definition.negated`、`Format.negated`），电表 A 的功率就是这样处理的，寄存器中购电为正，而读数与其他每个电网功率一样以馈电为正；电表 B 是光伏电表，不取负。位字段可以取反（`Definition.inverted`、`Format.inverted`），在编解码器中解码和编码，`ev_ems_charging` 就是这样在寄存器位为 0 时显示充电为开，同时打包字段的读取-修改-写入保持其他位不变。型号的 `Replacement` 可以把一个组合键变成单个有地址的寄存器（`uncombined`），H2 就是这样从一个 16 位寄存器读取每个并机功率，而 HS3 在相同的键下继续组合低字和高字。

## 轮询

功能列表的 [轮询](../../../custom_components/saj_local/docs/features.md#polling) 和 [保护逆变器](../../../custom_components/saj_local/docs/features.md#protecting-the-inverter) 两节列出了相关代码。

库决定读取什么和何时读取，并保护设备；集成只负责呈现结果。轮询规则位于库中，因为这些规则描述的是设备，而不是 Home Assistant，因此没有任何集成代码可以绕过这些规则。

- **计划、预算、健康状况和轮询器**（`saj/schedule.py`、`budget.py`、`health.py`、`poller.py`）各自负责一个决定，并把时间和等待作为输入。这四个模块都不读取时钟，也不休眠，这使其测试可以即时、确定地运行。只有客户端的默认值和协调器的接线会接触真实时间。
- **每个安装一个共用的时间网格。** 相互错开的节奏永远不会共用一次请求；共用的网格让同时到期的时刻可以一起规划，而丢弃错过的时刻可以避免超时演变成积压。
- **请求预算是设备的属性。** 预算按请求计数，因为现场反馈描述的就是请求，并且预算是库中的常量而不是设置，这样任何配置都无法超出预算。等待预算会延长一个周期，而不是丢弃读取。
- **应答要分类，而不是只当作成功或失败。** 被拒绝的寄存器是健康设备的一种应答，只影响其传感器；只有忙碌和设备故障代码以及链路错误才会使一个周期失败。因此一个被拒绝的数据块不会使每个实体来回跳变。
- **失败的周期会退避，并且绝不在周期内重试。** 重试恰恰在模块吃力时成倍增加负载。唯一的例外是保持的连接已过时，这不是设备故障：连接会被重新打开，标识会被核实，该周期变成一次完整读取，因此没有任何已发布的值早于这次重新连接。
- **预算和退避属于端点，而不属于某次加载**（`saj/guard.py`）。重新加载、编辑组或设置重试都会构建新的客户端，而由客户端保存的预算或失败计数每次都会从零开始，模块就是这样被 Home Assistant 自己的重试压垮的。集成在 `hass.data` 中为每个主机和端口保留一个保护器，其生命周期与 Home Assistant 相同，并把它交给每个客户端和轮询器，包括设置或“配置”检查所用的临时客户端。加载时先询问保护器，并在打开连接之前报告尚未就绪，而用户发起的检查会绕过退避，但不会绕过预算。通过的检查会重置退避，因为设备刚刚应答过，随后的加载不应因已经恢复的故障而被拒绝；失败的检查不会改变任何内容，因此用户重试错误的地址既不能延长也不能抹去保护。
- **轮询组是配置子条目。** 子条目让集成页面具备原生的添加、编辑和删除功能，而无需更改设置或“配置”。组存储语义化的实体键（`keys`），绝不存储实体 ID，并且实体绝不附属于某个子条目，因为 Home Assistant 会删除被删除子条目的实体，而组不能带走传感器或其历史记录。
- **只为被读取过的传感器写入状态**，或其可用性发生变化的传感器写入状态，因此快速的组不会使缓慢的传感器看起来已刷新。
- **唤醒时间向上取整。** Home Assistant 以整秒调度协调器，提前触发的唤醒会发现没有任何内容到期，白白浪费一个时间片。

## 设备故障和修复问题

功能列表的 [设备故障和修复问题](../../../custom_components/saj_local/docs/features.md#device-faults-and-repairs) 和 [更换型号](../../../custom_components/saj_local/docs/features.md#model-replacement) 两节列出了相关代码。

故障是与型号无关的键，在每个上报该故障的型号上名称相同。型号在其 `Profile.faults`（`saj/models/hs3.py`、`h2.py`）中声明哪些故障字的哪些位上报每个键，故障字本身是普通的已布局行，绝不是实体（`Definition.exposed` 为 false）。位的位置是数据，因此更正某个位置不会改变任何键。两个型号以相同方式上报的条件在 `saj/models/shared_faults.py` 中共用；型号只列出自己不同的部分。

目录根据该映射而不是根据布局来构建故障实体：每个具有故障字的设备，各有具名故障、未识别行和汇总行，每个都是组合行，其 `ANY_BIT` 操作测试其来源字的位。汇总还读取电池包的字，这些字是 `battery_pack_faults` 系列的普通行。目录构建会拒绝不是已布局行的字、不在任何故障字中或超出其字的来源、被两个故障同时占用的位，以及其字属于其他设备的故障。无论依据如何，故障行都默认启用，因为用户为每个故障都选择了这样做，规划器会把这些行的来源字放入已经发出的请求中（只要该数据块本来就要读取）。`hidden_sources` 向协调器提供已启用故障实体背后的字，因此即使没有实体显示这些字，也会读取这些字，诊断和故障日志使用原始字。把字解码为当前故障和未识别位，以及把两次读数转换为已触发和已清除的故障的监视，都是纯库代码（`saj/faults.py`）。

所有问题 ID 及其触发和移除都位于 `issues.py`：设备、型号、拒绝和不可达问题。库的错误从不在那里导入；`errors.translate_error` 提供翻译键和占位符，用来判断某个错误是否属于型号发现。拒绝问题把其键保存在问题数据中，因此重新加载（会启动新的 `ReadHealth`）之后，仍然可以清除现在已应答的键。不可达问题读取端点保护器的开始失败时间（`saj/guard.py`），该时间与保护器的其余部分一样在重新加载后依然保留，并在每个失败的周期和每次加载尝试时检查，包括被退避终止的加载。

修复是 Home Assistant 的修复流程（`repairs.py`）。型号修复不会重复“配置”：`config_flow.py` 中的 `EntryChanges` 保存“配置”和修复共用的验证、冲突检查和保存，修复用已保存的设置和设为“自动”的型号调用 `EntryChanges`。对于已加载的安装，验证会借用协调器的客户端（`async_validation_session`），该客户端在会话结束时关闭，即使失败也是如此。随后会话请求一次刷新，作为任务调度，这样表单不必等待轮询，并在周期锁释放之后运行。该轮询会看到已断开的客户端，并通过 `Poller._reopen` 重新连接，该方法负责标识检查；已连接的客户端会跳过标识检查，在检查运行之前，写入和心跳会因未连接而被拒绝。不可达问题在 15 分钟之后的第一次失败重试时出现，退避使其在故障发生后 15 到 20 分钟时出现。

## 调试转储和日志

功能列表的 [诊断与调试日志](../../../custom_components/saj_local/docs/features.md#diagnostics-and-debug-logging) 一节列出了相关代码。

寄存器存储器（`saj/memory.py`）位于 `ModbusTcpClient` 中，因为客户端是每次读取都必经的唯一位置：轮询、心跳、写入回读、检测和标识都不需要自己的代码就能向该存储器提供数据。该存储器按地址记录已应答的字，按地址和数量记录失败的范围，使用客户端自己的时钟，因此测试不需要真实时间。每个可能到达线路的 `ModbusErrorMessage` 在 `FAILURE_OUTCOMES` 中映射为四种结果之一：拒绝是 `exception`，两种超时都是 `timeout`，连接失败、对端关闭和应答不完整是 `connection_lost`，报头不匹配或长度、寄存器数量或确认格式错误是 `malformed_reply`。被拒绝的跨度或值绝不会到达线路，也不会被记住。写入不会作为读取被记住。当同一范围应答时，失败会被丢弃，字保留各自的存在时间，因此转储既显示最后一次良好的内容，也显示此后失败的内容。快照根据设备的目录行按需构建，因此按键分组在轮询期间不产生任何开销。

隐私在字所在的位置决定，而不是在显示的位置决定。`Definition.private` 标记内容可识别个人或网络的行；`private_rows` 给出这些行以及逆变器序列号范围（没有任何行覆盖该范围，但标识和 H2 标识块会读取该范围）。快照根本不携带私密的字，甚至不会交给集成，而是改为标记该条目；`diagnostics.py` 替换为 Home Assistant 的脱敏标记，从而使库不依赖 Home Assistant。只覆盖私密行一部分的读取，会整体被隐藏，因此部分重叠不会泄露任何字。设置、“配置”和修复表单的验证客户端不得污染转储：已加载条目上的“配置”会复用协调器的客户端，因此 `async_validation_session` 用 `ModbusTcpClient.unremembered` 包装该客户端。

日志（`saj/log.py`）必须为每一行加上系统标签，并保持 Home Assistant 每个集成的调试开关可用。`LabelledLogger` 是由每个模块自己的日志器构建的 `LoggerAdapter`，两件事都能做到，因为日志器名称不变，只有消息增加了前缀。标签由条目标题和创建条目时的序列号构建，这在读取标识之前就已知，因此连设置的第一行日志也有标签，并且标签会遮盖序列号（默认标题含有序列号），因此完整的序列号绝不会进入日志。`label.py` 为集成模块构建标签，设置时把同样的文字传给每个库对象，这些对象各自构建一个适配器。轮询行由轮询器根据经过其计数读取器的请求组装，因此失败的轮询仍会报告其发出的请求，包括被周期截止时间截断的请求，该请求会列为超时。

## 稳定名称

功能列表的 [设备与实体](../../../custom_components/saj_local/docs/features.md#devices-and-entities) 和 [实体 ID 与前缀](../../../custom_components/saj_local/docs/features.md#entity-ids-and-prefix) 两节列出了相关代码。

实体键是与用户编写的每个仪表盘和自动化之间的契约。库在各个 SAJ 型号之间提供同一套名称、单位和格式，因此硬件升级后，只要新旧系统有重叠的部分，历史记录就得以保留。在发明名称之前，先把新设备映射到现有词汇上。

实体 ID 属于同一契约。`const.py` 中的 `object_id` 和 `fixed_entity_id` 是定义该格式的唯一位置，其他一切（实体、前缀更改时的重命名、确认文本、诊断）都调用这两个函数。因此实体键是实体 ID 的一部分：重命名键是破坏性更改，重新措辞标签则不是。实体的唯一 ID 仍是配置条目 ID 加键（`entity_unique_id`），不受前缀更改影响。前缀是 Home Assistant 层面的问题，只存在于集成的条目选项中，绝不存在于 SAJ 库中。

前缀更改通过实体注册表重命名，因为这样才能让记录器把历史记录和统计数据带到新的 ID。记录器拒绝把统计数据移到已有统计数据的 ID 上，因此会先用一次元数据查询（`async_list_statistic_ids`）检查更改，并在保存更改时、第一次重命名之前，重复每一项检查。

## 写入

功能列表的 [更改设置](../../../custom_components/saj_local/docs/features.md#changing-settings)、[EMS](../../../custom_components/saj_local/docs/features.md#ems) 和 [功率控制](../../../custom_components/saj_local/docs/features.md#power-control) 三节列出了相关代码。

- **写入只有一条路径。** 实体操作调用 `SajEntity.async_change`，后者调用协调器唯一的 `write` 方法。EMS 清理使用同一把锁和同样的错误处理。心跳不是写入：心跳通过库的 `keep_alive_read_ems` 读取每个所拥有功能的目标，然后在同一个周期锁之下，通过限值读取来读取 EMS 限值，并且不使用写入配额。只有 `custom_components/saj_local/errors.py` 可以导入库的错误；其余代码都通过它处理。
